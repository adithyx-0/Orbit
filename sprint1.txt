CATEGORY 1: WHY THIS PROJECT / MOTIVATION
--------------------------------------------------------------------------------

Q1: Why did you choose this project?
A:  Digital subscriptions are a growing problem - the average person has
    7-12 active subscriptions but doesn't know their total monthly spend.
    Existing tools track either expenses OR screen time, but never connect
    the two. We saw an opportunity to bridge that gap with usage-aware
    financial analytics.

Q2: What problem are you actually solving that isn't already solved?
A:  The KEY unsolved problem is correlating COST with USAGE. Apps like
    Mint track what you pay. Android Digital Wellbeing tracks screen time.
    But nobody tells you "your Netflix costs Rs.15/hour because you only
    watched 10 hours this month." That's what PROSIT does.

Q3: Who is your target user?
A:  Students and young professionals aged 18-35 who have multiple digital
    subscriptions across entertainment, productivity, and learning
    platforms, and want to optimize their spending.

Q4: Is this just a fancy expense tracker?
A:  No. An expense tracker shows you what you spent. PROSIT shows you
    whether that spending was WORTH IT by measuring actual usage time
    against cost, computing ROI, and recommending optimizations.

Q5: Why not just use a spreadsheet?
A:  A spreadsheet requires manual tracking of both expenses AND usage time
    across devices. PROSIT automates the usage collection through device
    agents and automatically computes analytics. The value is in the
    automation and intelligence layer.

Q6: How is this different from Mint / CRED / Walnut?
A:  Those apps focus on bank transaction tracking and require bank API
    access (privacy risk). They show what you paid but not how much you
    used the service. PROSIT is privacy-first (no bank integration) and
    usage-aware (tracks actual app usage time via device agents).

Q7: How is this different from Android Digital Wellbeing or iOS Screen Time?
A:  Digital Wellbeing only tracks usage on ONE device and has no financial
    component. PROSIT aggregates usage across MULTIPLE devices (Android +
    Windows) and correlates it with subscription cost data.

--------------------------------------------------------------------------------
CATEGORY 2: TECHNOLOGY STACK CHOICES
--------------------------------------------------------------------------------

Q8: Why React.js and not Angular or Vue?	
A:  React has the largest ecosystem, best community support, and our team
    has prior experience with it. Its component-based architecture suits
    our dashboard-heavy UI. Angular is heavier and more opinionated than
    we need. Vue is viable but has a smaller ecosystem for charting
    libraries.

Q9: Why Next.js? Why not plain React?
A:  Next.js gives us server-side rendering (SSR) for faster initial page
    loads on the dashboard, built-in routing, and API routes that can
    serve as a lightweight BFF (Backend For Frontend). However, we're
    still evaluating whether we need SSR - if not, plain React with
    Vite would suffice.

Q10: Why Node.js for backend? Why not Python/Django or Java/Spring Boot?
A:  Node.js with Express is lightweight, non-blocking (good for handling
    concurrent API calls from multiple device agents), and uses JavaScript
    end-to-end with our React frontend, reducing context switching.
    Django is great but heavier than we need. Spring Boot is enterprise-
    grade overkill for an academic project.

Q11: Why PostgreSQL and not MongoDB?
A:  Our data is highly relational: Users own Subscriptions, which have
    UsageRecords, which feed AnalyticsResults. These relationships with
    foreign keys and joins are best served by a relational database.
    MongoDB (document-based) would require denormalization and make
    complex analytics queries harder.

Q12: Why not Firebase/Firestore?
A:  Firebase is good for real-time apps and rapid prototyping, but it's
    a NoSQL document store with limited query capabilities for complex
    aggregations (like cost-per-hour calculations across multiple
    collections). Also, vendor lock-in to Google.

Q13: Why Kotlin for Android and not Flutter or React Native?
A:  We need OS-level access to Android's UsageStatsManager API for
    tracking foreground app usage. Cross-platform frameworks like Flutter
    or React Native have limited access to these system-level APIs.
    Kotlin is the official Android language with full API access.

Q14: Why Python for the Windows agent? Why not C#?
A:  Python with psutil and pywin32 provides easy access to Windows
    process monitoring without the complexity of a full .NET setup.
    It's cross-platform friendly, has excellent libraries for system
    monitoring, and is faster to develop. C# would be more performant
    but adds development overhead.

Q15: Why JWT for authentication? Why not sessions or OAuth?
A:  JWT is stateless - the server doesn't need to store session data,
    which simplifies scaling. It also works well for our device agents
    (Android app, Windows agent) which need to authenticate API calls
    without browser cookies. OAuth is for third-party login (Google,
    GitHub) which we don't need in Sprint 1.

Q16: Why Tailwind CSS and not Bootstrap or Material UI?
A:  Tailwind gives utility-first styling with full customization control
    and smaller bundle sizes (tree-shaking). Bootstrap is opinionated
    with a dated look. Material UI is good but heavier and Google-styled.
    Tailwind lets us build a unique, responsive design efficiently.

Q17: Why Chart.js for visualization?
A:  Chart.js is lightweight, easy to integrate with React, and supports
    all the chart types we need (bar, line, pie, doughnut for spending
    breakdowns). Recharts is also an option (React-native charting)
    but Chart.js has more community plugins.

Q18: Why not use a microservices architecture?
A:  Microservices add complexity in deployment, inter-service communication,
    and debugging that isn't justified for a 3-person academic project.
    A monolithic Node.js backend with clear module separation gives us
    the same code organization benefits without operational overhead.
    We can always decompose later if needed.

Q19: What deployment platform will you use?
A:  Vercel for the frontend (free tier, optimized for Next.js/React),
    and either Railway or Render for the Node.js backend + PostgreSQL
    (both offer free tiers). Alternatively, AWS free tier with EC2 + RDS.

--------------------------------------------------------------------------------
CATEGORY 3: ARCHITECTURE & DESIGN DECISIONS
--------------------------------------------------------------------------------

Q20: Explain your system architecture.
A:  Client-server architecture with 4 layers:
    1. Frontend: React web dashboard (presentation layer)
    2. Backend: Node.js/Express API server (business logic layer)
    3. Database: PostgreSQL (data layer)
    4. Device Monitoring: Android app (Kotlin) + Windows agent (Python)
       that push usage data to the backend via REST APIs.

Q21: Why MVC pattern? Why not something else?
A:  MVC (Model-View-Controller) cleanly separates concerns:
    - Model (Entity classes) = data/database
    - View (Boundary classes) = UI components
    - Controller = business logic and orchestration
    This makes the codebase modular, testable, and maintainable.

Q22: What is the "composition" relationship in your class diagram?
A:  Composition means the child cannot exist without the parent.
    AnalyticsResult is composed within Subscription - if you delete a
    subscription, its analytics results must also be deleted because
    they have no meaning on their own. This is stronger than association
    (where both can exist independently).

Q23: Why did you decompose the Analytics Engine (P4) to Level 2?
A:  The Analytics Engine is the most complex and differentiating part of
    our system. Level 1 shows it as a single process, which doesn't
    capture the internal pipeline: aggregate -> compute cost ->
    compute ROI -> recommend -> evaluate goals. Level 2 makes this
    pipeline explicit and testable.

Q24: How do the device agents communicate with the backend?
A:  Via REST API calls over HTTPS. The agents periodically batch usage
    data (app name, duration, timestamp) and POST it to a dedicated
    endpoint (/api/usage). The agent authenticates using the user's
    JWT token. Data is sent in JSON format.

Q25: What happens if the device agent can't reach the server?
A:  The agent stores data locally (SQLite on Android, JSON file on
    Windows) and retries when connectivity is restored. This is a
    store-and-forward pattern that ensures no data loss.

Q26: How do you handle data from multiple devices for the same user?
A:  Each UsageRecord has a deviceType field (Android/Windows). The
    Analytics Engine aggregates records across all devices for a given
    user and subscription to compute unified metrics.

Q27: What is the role of the Notification Service in your architecture?
A:  It's an external service (Firebase Cloud Messaging for push,
    SendGrid for email) that we delegate to for delivery. Our backend
    composes the notification payload and triggers the service. We don't
    build our own email/push infrastructure.

CATEGORY 4: UML DIAGRAMS
--------------------------------------------------------------------------------

Q28: Why did you choose these specific UML diagrams?
A:  Use Case Diagram - captures functional scope and actor interactions.
    Activity Diagram - models user workflow and decision logic.
    DFD (Levels 0-2) - shows data flow between system components.
    Class Diagram - defines the static structure and relationships.
    These four cover requirements, behavior, data flow, and structure -
    the four essential SE modeling perspectives.

Q29: What are <<include>> and <<extend>> in your Use Case diagram?
A:  <<include>>: mandatory sub-behavior. Example: "Add Subscription"
    always INCLUDES "Login" - you can't add a subscription without
    being authenticated.
    <<extend>>: optional behavior. Example: "Track Goal Progress"
    EXTENDS "Set Goals" - you can set goals without tracking them, but
    tracking is an optional extension.

Q30: Why do you have both an Activity Diagram and a DFD?
A:  They model different things. The Activity Diagram shows the USER'S
    behavioral flow (what steps they take). The DFD shows how DATA
    moves through the SYSTEM components. Both perspectives are needed
    for a complete understanding.

Q31: What are the data stores in your DFD Level 1?
A:  DS1: Users DB (profiles, credentials)
    DS2: Subscriptions DB (subscription records)
    DS3: Usage Records DB (app usage sessions from devices)
    DS4: Goals DB (user-defined targets)
    DS5: Analytics Results DB (computed metrics)

Q32: How many actors are in your Use Case diagram and why?
A:  6 actors:
    - Guest/New User (registers)
    - Registered User (primary - uses all features)
    - Admin (manages users)
    - Android App (system actor - sends usage data)
    - Windows Agent (system actor - sends usage data)
    - Notification Service (external - delivers alerts)
    We separated Android App and Windows Agent because they have
    different APIs and data formats.

Q33: Why is the Notification Service shown as an actor, not part of system?
A:  Because it's an EXTERNAL service (Firebase/SendGrid) that we don't
    build or control. In UML, actors are entities external to the system
    boundary that interact with it. We send notification payloads TO it;
    it handles actual delivery.

CATEGORY 5: SOFTWARE ENGINEERING CONCEPTS
--------------------------------------------------------------------------------

Q34: What SDLC model are you following and why?
A:  Agile (iterative/incremental). Because:
    1. Requirements may evolve as we build and test.
    2. We can deliver working increments each sprint.
    3. Suits a small team (3 members) with regular feedback cycles.
    4. Better than Waterfall for a project where we're learning and
       iterating on the tech stack.

Q35: Why not Waterfall?
A:  Waterfall requires all requirements upfront and doesn't accommodate
    changes well. Our project involves device agents where we'll
    discover platform limitations only during development. Agile lets
    us adapt sprint-by-sprint.

Q36: Why not Spiral model?
A:  Spiral is risk-driven and suited for large, high-risk projects with
    formal risk analysis phases. Our project is moderate-scale academic
    work. Agile gives us the iterative benefits without the overhead of
    formal risk assessment documents each cycle.

Q37: What is the Elaboration Phase you mentioned?
A:  In the Unified Process (and in Agile contexts), Elaboration is where
    you finalize architecture, resolve major technical risks, and
    complete detailed design. Sprint 1 is our elaboration - we've done
    requirements, UML modeling, and architecture design. Sprint 2 moves
    into Construction (actual coding).

Q38: What elicitation techniques did you use?
A:  1. Brainstorming - team discussions to generate feature ideas and
       identify user pain points.
    2. Observation - studying how real users interact with subscription
       services and manage digital time.
    We chose these because with a 3-person team, formal interviews or
    surveys were less practical.

Q39: What are your functional vs non-functional requirements?
A:  Functional: User registration/login, subscription CRUD, device usage
    tracking, analytics dashboard, cost-per-hour calculation, reports,
    goal setting.
    Non-functional: Security (encrypted data), Privacy (user consent),
    Performance (efficient analytics), Scalability (multi-user),
    Usability (intuitive UI), Reliability (consistent uptime).

Q40: How did you do your feasibility study?
A:  Four aspects:
    1. Technical: All technologies (React, Node, PostgreSQL, Android APIs)
       are mature and well-documented.
    2. Economic: Open-source stack + free-tier cloud = minimal cost.
    3. Operational: Web-based UI requires no technical expertise from users.
    4. Schedule: Modular design allows parallel development by 3 members.

--------------------------------------------------------------------------------
CATEGORY 6: PRIVACY, SECURITY & ETHICS
--------------------------------------------------------------------------------

Q41: Isn't tracking device usage a privacy concern?
A:  Yes, which is why privacy is a core design principle:
    1. Explicit opt-in consent required before any monitoring.
    2. We only track app NAME and DURATION - never content, keystrokes,
       or personal data within apps.
    3. Users can pause or disable monitoring at any time.
    4. Manual-first approach: users can also manually log usage.
    5. No bank/financial API integration.

Q42: How do you store passwords?
A:  Passwords are hashed using bcrypt (one-way hash with salt) before
    storage. We never store plaintext passwords. JWT tokens have
    expiration times and are transmitted over HTTPS only.

Q43: What if someone intercepts the usage data from agents?
A:  All communication between device agents and backend uses HTTPS
    (TLS encryption in transit). The agent authenticates with a JWT
    token. Data at rest in the database is also encrypted.

Q44: Do you comply with GDPR / data protection?
A:  Yes, in principle:
    - Users must consent before monitoring begins.
    - Users can request data deletion (right to erasure).
    - We collect minimal data (app name + duration only).
    - No data is shared with third parties.

--------------------------------------------------------------------------------
CATEGORY 7: METRICS & ANALYTICS
--------------------------------------------------------------------------------

Q45: How do you calculate cost-per-hour?
A:  Cost-per-hour = (Monthly subscription cost) / (Total hours used
    that month). Example: Netflix Rs.499/month, used 20 hours =
    Rs.24.95/hour. If used only 5 hours = Rs.99.80/hour.

Q46: How do you calculate ROI?
A:  ROI = (Value derived - Cost) / Cost. We estimate "value derived"
    using utilization rate: if you're using a service heavily relative
    to its cost category, ROI is high. A learning platform used 30
    hours/month at Rs.500 has higher ROI than one used 2 hours at Rs.500.

Q47: What is "opportunity cost" in your context?
A:  The value you lose by paying for unused subscriptions. If you pay
    Rs.500/month for a service you use 1 hour, the opportunity cost is
    what else you could have done with that Rs.500 (e.g., a different
    service you'd actually use).

Q48: What is "utilization efficiency"?
A:  A percentage metric: (Actual usage hours) / (Expected/benchmark
    usage hours) * 100. If you subscribe to a learning platform
    expecting to use it 20 hours/month but only use 5, your utilization
    efficiency is 25%.

Q49: How does the recommendation engine work?
A:  Rule-based in Sprint 1 (not ML yet):
    - If utilization < 20%: "Consider cancelling or downgrading"
    - If cost-per-hour > category average: "You're overpaying for usage"
    - If usage is only on one device: "Install agent on other devices
      for better tracking"
    Later sprints may add ML-based pattern recognition.

Q50: What kind of reports does the system generate?
A:  Weekly/monthly summaries including: total spend, per-subscription
    cost-per-hour, usage trends (increasing/decreasing), ghost
    subscription alerts, goal progress, and actionable recommendations.

CATEGORY 8: TRICKY / CHALLENGING QUESTIONS
--------------------------------------------------------------------------------

Q51: This seems very ambitious for 3 people in one semester. Is it feasible?
A:  Yes, because we're building in sprints with clear scope boundaries.
    Sprint 1 (done): requirements + design.
    Sprint 2: backend API + one device agent prototype.
    Sprint 3: frontend dashboard + integration.
    We focus on the core loop (subscription CRUD + usage tracking +
    basic analytics) first. Advanced features are stretch goals.

Q52: You haven't written any code yet. What have you actually done?
A:  Sprint 1 is the ELABORATION phase - this is standard in Agile/UP.
    We've completed: problem definition, stakeholder analysis, feasibility
    study, 17 use cases with full descriptions, activity diagram, DFDs
    (3 levels), class diagram with 19 classes, and technology stack
    selection. This foundation prevents costly rework during coding.

Q53: Why do you need BOTH Android and Windows agents? Isn't one enough?
A:  Users consume subscriptions across devices. You might watch Netflix
    on your phone but use Adobe Creative Cloud on your laptop. Tracking
    only one device gives an incomplete picture. Cross-device aggregation
    is a key differentiator.

Q54: What if the user doesn't install the agents? Does the system still work?
A:  Yes. The agents are optional enhancements. Users can manually log
    their usage time. The analytics engine works with whatever data is
    available. Agents just automate the data collection.

Q55: How do you map app usage to a specific subscription?
A:  The user specifies which apps are associated with each subscription
    when they add it. E.g., "Netflix" subscription maps to the Netflix
    app on Android and Netflix.exe on Windows. The system uses app name
    matching.

Q56: What if an app name on Android is different from Windows?
A:  The Subscription entity has metadata fields for app identifiers per
    platform. The user can configure "com.netflix.mediaclient" for
    Android and "Netflix.exe" for Windows under the same subscription.

Q57: Why not use Plaid or similar for automatic subscription detection?
A:  Plaid requires bank account access, which introduces significant
    privacy and security risks. It also requires paid API access.
    Our manual-first approach is safer, free, and gives users full
    control over what data enters the system.

Q58: What happens when a subscription price changes?
A:  The user updates the subscription cost through the Edit Subscription
    use case. The system uses the current cost for forward-looking
    analytics and can show historical cost trends if we store price
    change history.

Q59: How is your system scalable?
A:  Stateless JWT auth allows horizontal backend scaling. PostgreSQL
    supports connection pooling and read replicas. The frontend is a
    static SPA that can be served via CDN. Device agents are independent
    and only push data periodically.

Q60: What testing strategy will you use?
A:  Unit tests for analytics calculations (cost-per-hour, ROI formulas).
    Integration tests for API endpoints (using Jest/Supertest).
    Manual testing for device agents on actual Android/Windows devices.
    End-to-end testing for the dashboard using Cypress or Playwright.

CATEGORY 9: QUICK-FIRE CONCEPTUAL QUESTIONS
--------------------------------------------------------------------------------

Q61: What is a Use Case?
A:  A description of a specific interaction between an actor and the
    system to achieve a goal. It captures WHAT the system does, not HOW.

Q62: What is the difference between <<include>> and <<extend>>?
A:  <<include>> = mandatory (always happens).
    <<extend>> = optional (may or may not happen, based on conditions).

Q63: What is a DFD?
A:  Data Flow Diagram - shows how data moves through a system. Uses
    processes (circles), data stores (open rectangles), external entities
    (rectangles), and data flows (arrows).

Q64: Difference between DFD Level 0, 1, and 2?
A:  Level 0 (Context): entire system as one process with external entities.
    Level 1: decomposes into major sub-processes.
    Level 2: further decomposes a specific sub-process (we did P4).

Q65: What is composition vs aggregation?
A:  Composition: child CANNOT exist without parent (AnalyticsResult
    cannot exist without Subscription - strong ownership).
    Aggregation: child CAN exist independently (a student can exist
    without a class - weak ownership).

Q66: What are Entity, Boundary, and Control classes?
A:  Entity: data/business objects (map to DB tables).
    Boundary: UI components or external interfaces.
    Control: business logic / orchestration (controllers).
    This is the Robustness/BCE pattern, aligned with MVC.

Q67: What is JWT?
A:  JSON Web Token - a self-contained token with encoded user identity
    and expiration. The server signs it with a secret key. Client sends
    it in every request header. Server verifies without database lookup.

Q68: What is REST API?
A:  Representational State Transfer - an architectural style for web APIs
    using HTTP methods (GET, POST, PUT, DELETE) on resource URLs.
    Stateless, cacheable, and uniform interface.

Q69: What is Agile methodology?
A:  An iterative approach to software development emphasizing:
    working software over documentation, customer collaboration,
    responding to change, and individuals/interactions.

Q70: What is a Sprint?
A:  A fixed-length iteration (typically 2-4 weeks) in Agile where a
    defined set of work is completed and delivered.


================================================================================
FINAL TIPS FOR THE VIVA
================================================================================

1. CONFIDENCE > CORRECTNESS
   If you don't know an answer, say: "That's an interesting point.
   We haven't finalized that decision yet, but our current thinking
   is..." Then give your best reasoning.

2. NEVER SAY "I DON'T KNOW" ALONE
   Always follow with: "...but based on [principle/reasoning], I would
   approach it by..."

3. DEFEND YOUR CHOICES WITH TRADE-OFFS
   Don't just say "we chose X." Say "we chose X over Y because [reason],
   though we acknowledge Y's advantage in [area]."

4. USE THE WORD "BECAUSE"
   "We chose PostgreSQL BECAUSE our data is relational."
   "We avoided bank APIs BECAUSE of privacy risks."
   Reasoning > declarations.

5. TEAM COORDINATION
   If one person is asked a question they struggle with, another can
   step in: "If I may add..." This shows teamwork.

6. ANTICIPATE FOLLOW-UPS
   If you say "we use JWT", expect: "Why not sessions?" or "How do you
   handle token expiration?" Have the next level of depth ready.

7. STAY CALM UNDER RAPID FIRE
   If the professor asks many quick questions, take a breath before each
   answer. Short, confident answers beat long, rambling ones.

8. OWN YOUR DESIGN DECISIONS
   Don't say "we just picked it." Say "we evaluated [options] and chose
   [X] because it best fits our [constraint/requirement]."
